# Outlook同期：パターン別の対応・検証表

確認日：2026-10-09。対象はWindowsのClassic Outlookです。

通常予定の双方向同期、削除・キャンセルの反映を修正しました。ただし、Outlookの全機能・全形式への対応ではありません。以下では、正常反映、保留、編集非対応、未実機検証を分けています。

Outlook側の変更は「今すぐ取得」または設定した自動同期の実行時に確認します。リアルタイムの変更通知ではありません。新規に取り込む予定は選択した取得元・期間で絞り込み、識別情報を保存済みの連携予定は登録先で個別に確認します。

## 1. 重複しない状態区分

上から該当する行に分類します。作成元と、現在連携しているかは別の情報です。

| 区分 | 条件 | 同期の扱い |
|---|---|---|
| S1 | 連携履歴があり、登録OFF | Outlookへの削除反映後はアプリ内だけで保持。Outlookで復元されても勝手に再連携しない |
| S2 | 連携ON、ローカルのタスクは削除済み | 未完了の削除は送信。削除済みの記録を残し、取り消し・確認できた外部復元を処理 |
| S3 | 連携ON、タスクあり、送信待ち・処理中・失敗中 | ローカル変更を保持。古い取得結果は上書きせず、競合・確認不能を表示 |
| S4 | 連携ON、反映完了、アプリで作成 | 同じ連携キー・登録IDで双方向に照合 |
| S5 | 連携ON、反映完了、Outlookから取得 | 元のOutlookの予定に対して更新・削除。別の予定を作り直さない |
| S6 | Outlookのキーはあるが連携先の識別情報がない旧形式 | 同じ予定を確認できたときに移行。明示的なキャンセルは反映。所在不明だけでは削除しない |
| S7 | Outlookキーも連携履歴もないローカル予定 | Outlookの取得・削除・キャンセルでは変更しない |

S3の「待ち・処理中・失敗」と取得結果の組み合わせは、後述の保護条件を適用します。

取得結果は「確認不能」「対象を確認でき、取消済み」「対象を確認でき、有効」「対象の不在を確認」の4つに分類します。有効な予定は、保存済みの比較情報と比べて「変更なし」「変更あり」「初回で比較情報なし」に分けます。確認不能と不在を混同しないことが、誤削除を防ぐ条件です。

予定の形式は「アプリで表現できない形式」「表現可能なOutlook原生の繰り返し」「表現可能な通常予定」に分類します。繰り返しは系列全体と1回を区別します。次表はこの状態・取得結果・形式に対する操作別の確認表であり、全提供元で全組み合わせを実機試験したという意味ではありません。

## 2. 操作別の対応

「実機」は一時的な検証用予定表に対するCOM操作と、実際のSQLite同期処理による確認です。検証用予定表は終了時に削除します。「自動」は外部Outlookを使わない回帰テストです。

| 変更した側・操作 | 結果 | 確認 |
|---|---|---|
| アプリで新規作成、登録ON | 選択した登録先へ1件作成 | 実機 |
| アプリで新規作成、登録OFF | Outlookへ送信しない | 自動・既存UI試験 |
| 初回送信前にON→OFF→ON | 存在しない予定の復元を試みず、初回登録を行う | 実機 |
| OFF反映後にON→送信前にOFF→再度ON | 前回の削除実績を保持し、削除済みアイテムにある元予定を復元 | 実機 |
| アプリでタイトル・日時・メモを変更 | 元のOutlook予定を更新 | 実機 |
| アプリで削除／登録OFF | 対応するOutlook予定を削除。OFF時はローカルタスクを保持 | 実機・自動 |
| 完了した通常予定の削除をアプリで取り消す | 削除済みアイテムに残る元の予定を元の予定表へ戻す | 実機 |
| Outlookで通常予定を作成 | 取得元・期間内の予定を1件取り込み、元の登録IDで連携 | 実機 |
| Outlookでタイトルと時刻を同時変更 | ローカルのID・タグを保ったまま更新 | 実機 |
| Outlookで本文を変更 | アプリのメモへ反映 | 実機 |
| 時間指定↔終日を切り替える | 時刻と終日状態を反映 | 実機 |
| Outlookで削除 | 連携先で不在を確認してローカルから削除。削除を送り返さない | 実機 |
| Outlookでキャンセル | 会議状態の取消を確認してローカルから削除 | 実機・状態値の自動試験 |
| 開始済み・過去の終日予定をOutlookで削除 | 保存済みの連携先を個別確認し、次の取得で反映 | 実機 |
| Outlookで通常予定を復元 | 確認できた同じ予定をローカルに復元し、タグ・IDを維持 | 実機・自動 |
| アプリ由来の繰り返しの1回を復元 | アプリ側の系列ID・繰り返し情報も保持 | 自動 |
| Outlook原生の日次繰り返しの1回をアプリで編集・削除 | その回だけを処理し、系列のマスターは削除しない | 実機 |
| Outlook原生の日次繰り返しの1回をOutlookで削除 | 削除済み例外を確認して該当回だけをローカルから削除 | 実機 |
| Outlookの繰り返し系列全体をキャンセル | マスターの取消状態を確認できた連携済みの各回を削除 | 状態判定・処理経路の確認。取消通知の送受信を含む実機試験は未実施 |
| 登録OFF→ローカル削除→Outlookで復元 | 元の識別情報を保持して、自動で再登録ONにしない | 自動 |
| 内容が同じでもOutlookの識別子が異なる予定 | 新しい識別情報を持つ予定は別件として取り込む | 自動 |

取得元から取り込んだ予定の更新先は、その元の予定です。「登録先の予定表」の設定変更で、既存の連携予定を別予定表へ移しません。

取消判定はタイトルの文言ではなく、会議状態とMAPIの取消フラグを使います。実際に受信済みの取消予定2件は、ユーザーデータのコピーでローカルからの削除を確認しました。繰り返しの例外は元の日時を一意に特定できる場合に処理します。試験中の未送信会議では取消指定が保存後に残らない場合があったため、その結果を系列全体の取消成功とは扱っていません。

## 3. 正常反映より優先する保護条件

| 条件 | 挙動 | 確認 |
|---|---|---|
| Outlookとアプリが未同期のまま同じ予定を変更 | 自動上書きせず競合にする。内容確認後の「再試行」でアプリ側を優先 | 実機 |
| 再試行時にOutlookの予定が複数日などの非対応形式へ変化 | 強制再試行でも形式の保護を解除しない | 実機 |
| 取得開始後にタスク・送信ジョブが変更された | 取得前の版と照合し、古い応答の反映を保留 | 自動 |
| 取得元を別の予定表に変更した | 別予定表で「見つからない」だけでは既存の予定を削除しない | 自動 |
| COMエラー・権限不足・途中終了・件数上限 | 不明を削除済みとみなさず保持し、エラーまたは警告を表示 | 自動・UI試験 |
| S_FALSE、検索の未検出、nullオブジェクト | 成功・未検出・本当の失敗を区別 | COM境界の自動試験・実機 |
| 同じ連携キー／復元候補が複数存在 | 曖昧な対象を変更せず、確認を求めるエラー | コード確認・一部自動試験 |
| Outlookが繰り返しの古い編集オブジェクトを保持 | 確認不能なら保持して警告。Outlookで開いている該当予定を閉じて再取得する | 実機で検出・保護動作確認 |
| 同期処理のDB書き込みが失敗 | トランザクションを取り消し、部分的なローカル削除を確定しない | 実装確認・既存DB試験 |

## 4. 制限・全対応としない項目

| 項目 | 現在の扱い |
|---|---|
| 複数日にまたがる予定 | アプリの形式では終了日を完全に表示できない。警告を出し、アプリでの内容編集を拒否する。Outlookで編集する |
| 秒単位の予定 | アプリが分単位のため、内容編集を拒否する。秒を黙って切り捨てて書き戻さない |
| Outlookの繰り返しルール作成・変更 | アプリからネイティブの系列ルールは編集しない。Outlookで変更する |
| 初めて取得する時点ですでに移動済みで、元の日時を特定できない繰り返し例外 | 誤った回を変更しないため編集を拒否。Outlookで操作する |
| Outlook原生の削除済みの1回をアプリのUndoで復元 | 元の例外を安全に復元できないため、Outlook側で復元するよう表示する |
| 元の予定を削除済みアイテムからも消した／復元候補が曖昧 | 元データを捏造・重複作成せずエラーにする。通常の復元成功とは区別する |
| 旧形式で取得元が不明、現在も見つからない予定 | 削除か別予定表かを断定できないため保持。既存キーの正の照合で移行する。旧データの追加確認は1回32か月まで |
| 予定表・ストア移動で登録IDも変わるケース | この環境で全パターンを実機確認していない。旧登録先の不在と移動の区別に制限がある |
| 週次・月次・年次の原生系列、各メール提供元、タイムゾーン・夏時間の全組み合わせ | OutlookのAPIに照会する経路はあるが、今回の日次系列の実機確認を全形式の検証として扱わない |
| 招待、参加者、出欠回答、更新・取消通知メールの送信 | アプリからの送信機能は対象外。Outlookで行う |
| 新しいOutlook | COM連携の対象外。Classic Outlookが必要 |

したがって「全形式・全操作に完全対応」とはしていません。通常予定の要求された双方向操作は確認し、識別不能・競合・未対応形式は保留または明示エラーにしています。

## 検証の入口

これまでの依頼との対応：

| 依頼 | 反映箇所・確認範囲 |
|---|---|
| `0x8007000e`、`0x0001`の登録失敗 | 空文字のCOM引数と成功値S_FALSEの扱いを修正済み。COM境界試験と実登録で確認 |
| タスク別に登録ON／OFFを選ぶ | 作成・編集画面と反映ジョブ。OFF時はOutlook側だけ削除し、タスクを残す |
| 登録の既定ON／OFF設定 | Outlook設定に保存。既存タスクへ一括適用しない |
| Outlookの予定表一覧から取得元・登録先を選ぶ | 候補取得・再取得と2つの選択欄。既存リンクは元の登録先を保持 |
| 双方向の作成・変更・削除・キャンセルを点検 | 本表、回帰試験、実Outlook試験。制限は上記に記載 |
| developに保存して起動 | 検証後にdevelopへ反映し、開発版を起動。以前の空プロファイルにユーザーが取り込んだ予定は再初期化しない |

- 状態・移行・競合・復元の自動試験：`src-tauri/src/outlook/reconcile.rs`
- 実Outlookの一時予定表による往復試験：`src-tauri/src/outlook/roundtrip_live_tests.rs`
- COM成功値、null、エラー、所有権：`src-tauri/src/outlook/enumeration_tests.rs`
- 警告・競合表示：`scripts/test-outlook-sync-status.mjs`
- 取得元・登録先の選択：`scripts/test-outlook-calendar-picker.mjs`

通常の全体検証は `cargo test --locked --manifest-path src-tauri/Cargo.toml` と `scripts/test-*`。実Outlook試験は通常は無効で、`cargo test --locked --manifest-path src-tauri/Cargo.toml live_bidirectional_matrix_in_temporary_calendar -- --ignored --nocapture` を明示実行します。
